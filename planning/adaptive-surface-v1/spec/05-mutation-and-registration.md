# Mutator, project declarations, and exceptional administration

## Same authority, a usable control-plane front door

Mutator can independently orient, inspect native source/skills, search, request a read-only investigation, evaluate evidence/impact/history, form a plan, and apply supported changes. It is not dependent on an observer preparing a proposal first. It does not need the observer's file/skill adapters or extended context mode.

Expose a small typed facade over existing `apply_proposal`, selective-replan, Todo lifecycle, retirement/supersession, and recovery/admin kernels. Do not publish raw SQL, arbitrary host commands, or the entire historical admin CLI as model tools. Normal coder workflow remains scoped; moving administrative capabilities into mutator does not make them available to coders through aliases.

## `plan`

Actions: `validate`, `diff`, `apply`, `amend`, `supersede`, `retire`. Validation/diff need no project mutation. Apply consumes a current native plan or prepared proposal using the existing kernel. Amend represents targeted changes to tasks, dependencies, scopes, interfaces, gates, run/lane bindings or related plan records as a semantic batch. Supersede and retire reuse complete affected-set derivation, preservation rules and canonical receipts.

The model supplies intent and canonical project entities. The server resolves exact affected records and reports a concise preview with semantic changes, retained successful outcomes/evidence, changed readiness, dirty-work treatment, expected authority version and source prerequisites. Do not force the caller to assemble private row digests, session tokens or every incidental ownership row.

Use current-state checks within the canonical transaction, not just a preflight check outside it. Bind reviewed changes to the relevant authority/record versions and source identities. Repeated operation IDs return their known receipt plus current readiness; they do not apply again. Real no-ops do not rewrite task versions, clear gates or churn projections. An unrelated source edit should not invalidate a declaration-only operation unless source identity is a genuine precondition. A changed reviewed affected set must not be silently recomputed and applied.

The existing kernels have distinct limits. A selective replan may refuse work with certain execution history; do not “fix” that by editing tables. Route to the supported preservation/supersession operation or report the actual missing capability and implement an additive canonical kernel transition. Keep successful terminal proof frozen. Current gate freshness for active work remains live.

## `amend_project`

One typed semantic operation for project declarations, with preview/apply and revision-aware idempotence. Initial actions:

| Action | Example intent | Validation |
|---|---|---|
| `register_identity` | Package/module/interface X at a version maps to registered repository Y | Canonical identity, access, version/environment; ambiguous mappings refuse |
| `register_relation` | This consumer uses this interface/configuration | Typed source/target locators; origin remains project-declared |
| `register_generation` | Output root/glob is generated by these inputs/tool | Relative roots, dependency read set, generator provenance; no automatic generator execution |
| `configure_provider` | Enable an installed registered provider or change permitted options | Trusted provider ID/options; never arbitrary executable/install permission |
| `remove_registration` | Retire a specific incorrect declaration | Exact ID/version, affected-resolution preview, history retained |
| `record_skill_use` | Skill route materially informed task/subsystem work | Skill identity/reason/anchors; distinguish consulted/applied |
| `update_orientation` | Publish a source-backed project purpose/map/constraint record | Anchors and field-level freshness; not a blind whole README summary |

A safe scoped coder can publish skill use, findings and candidate relationships through `coordinate_task(publish_context)` or existing completion/context hooks. Promotion to broad authoritative project declarations belongs to mutator under policy; no requirement for a second human confirmation for every ordinary additive fact. Automatic detection is system-produced evidence, not self-authorized agent prose.

Project-level records belong in the canonical Todo semantic authority (additive schema/read/export support as required). Root registration and principal/provider executable trust remain explicit host configuration. A mutator semantic mapping cannot grant itself access to another directory or run an arbitrary indexer.

Each semantic transaction increments the proper revision, emits a material event and invalidates only related derived graph/search/orientation fragments. Projection/index update failure is visible and repairable; it cannot roll back or lie about a committed semantic transaction. Support removal/renames without orphaned cached edges. Cross-project declarations do not merge Todo databases or create a fictitious distributed transaction.

## `maintain_execution`

Make the existing exact maintenance route available on mutator, with supported diagnose/prepare/execute handling rather than an operator-only maze. Preserve legacy opaque-mandate consumption for compatibility. Reuse current recovery, retirement, supersession, preserved-work and readiness-assessment kernels. Update description: the observed implementation already handles prepared supersession as well as clean stopped execution.

A safe maintenance journey derives the exact target, validates live ownership/executions/resources/workspaces, preserves dirty data, applies the approved logical transition, and returns a receipt and current valid next call. It does not reset/clean user files to force readiness. Live-child/gate/CUDA processes cannot be time-expired out of existence; coordinate with their canonical owners. Broad owner repair must not be accessible merely by a model claiming its role is root.

Normal ordinary coders no longer advertise general maintenance. A narrowly host-issued maintenance operator compatibility entry point may remain for already-issued grants, without granting broader plan powers. Mutator policy must not rely on legacy `self_debug` flags chosen by arbitrary callers.

## Human authorization: narrow, real, and explicit

Use a documented operation risk matrix based on actual effects, not alarming names. Routine additive registrations, plan edits, source-preserving rescoping and safe stopped-state repair should not demand repeated user rituals. Genuinely destructive actions—deleting retained work/artifacts/history, abandoning dirty work, overriding a demonstrably active mutator, removing trust boundaries, or similarly consequential operations—require the model to explain exact effects and ask for fresh explicit user permission before invocation. No blanket “approved:true” field authored by the same model proves permission.

Keep backend safety invariants even after permission. If the host/client can attest a user-confirmation event, bind it to exact scope, risk, version, expiry and a one-use authorization. Where the model interface cannot cryptographically distinguish a user message from model text, state honestly that the ask-first rule is an interaction policy; do not market it as proof. Existing trusted owner/host mechanisms remain the enforcement point for destructive operations. An untrusted repository note cannot grant permission.

Do not broaden this review into permission to delete existing source or automatically clean workspaces. There are few truly destructive cases; keep safe workflows direct while preserving the hard refusal conditions that protect concurrent work and retained evidence.
