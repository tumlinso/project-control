# 7. Acceptance, staged rollout, and measured value

## Deliver useful increments

The package has seven Project Control outcomes and two Skills transition outcomes, plus aggregate epic records. Each is a coherent deliverable; inspection, implementation, testing, review and ordinary retries happen inside it. The machine plans use one serial default lane per authority. Independent bounded work may be delegated without multiplying durable tasks.

**First:** adopt current source and decisions, build the fast evaluation seam, and preserve production. **Then:** move runtime ownership mechanically and establish continuation/lease semantics. **Then:** prepare useful evidence and connect focus/quiet/chat control. **Then:** add isolated empirical work. **Finally:** evaluate end-to-end usefulness and promote one qualified candidate.

An early demand-only deployment with prepared context can be worthwhile before every experimental behavior is enabled. Keep optional automatic experiments off until their authority and usefulness are proven. Do not make source migration an excuse for an unrelated rewrite of old harnesses or Todo internals.

## Mandatory scenario groups

`machine/acceptance.json` provides explicit cases, owners and expected observations. The core release properties are:

**Continuity and capacity.** Two waiting parents release both leases; child results resume the right generations once. A result arriving before wait registration is reconciled. Restart preserves progress. Cycles, runaway descendants and budget renewal are rejected. An interrupted effect is not duplicated blindly. Expired public work becomes terminal even if cleanup remains pending.

**Evidence quality.** Current notes cite exact source/experiment identities. A relevant material change invalidates them, unrelated changes do not blanket-invalidate everything, and removed evidence cannot remain silently authoritative. Exact public cache identity and historical warnings survive. The assistant does not turn its own prose into corroboration or silently promote canonical declarations.

**Usefulness.** A moving-source case demonstrates that an incoming question receives genuinely relevant prepared context. At least one scratch test exposes a real fixture defect or falsifies a hypothesis. A negative experiment is recorded accurately. A long-term goal cue is relevant and dismissible, not repetitive doctrine. Cross-workspace findings have actual witnesses and disclose incomplete coverage.

**Resource and permission safety.** Quiet windows survive restart; expired windows do not restart automatically. Repeated status calls load no model. Full GPU release is verified through the host interlock; external GPU work does not fight a rewarming loop. Sandbox restrictions hold for child processes, and the canonical source/dirty overlay/Git/Todo sentinels remain unchanged.

**Interface compatibility.** Preserve the exact current observer, coder and mutator tool sets, schemas, privilege checks, literal retries and response meanings unless a separately recorded operator decision changes one. No scheduler API leaks into normal MCP use. A scratch grant cannot be manufactured by source text, a cache hit or a role label.

## Performance and quality release criteria

Correctness and permission invariants are hard gates. Product economics are measured, not presumed. Before a real quality run, the root records baseline cases and a small explicit regression envelope for foreground latency and resource use. The acceptance file includes proposed starting objectives, not claimed measurements. Do not adjust targets after seeing results merely to pass.

Demonstrate at least one representative assisted workflow where the information materially helps and does not introduce misleading guidance. Compare foreground alone versus foreground with permitted background activity. Attribute cold startup, prefill, inference, tools, waits, cleanup and background preparation separately. Report median and spread; do not call a handful of trials a reliable p95 estimate. Use a larger replay or operational sample only where its cost is justified.

Practical starting objectives are: no model restart for a request-only policy change; zero inference calls during a no-change quiet reconciliation; no occupied model lease for an explicit dependency wait; materially fewer repeated source reads on a prepared repeated task; and no unbounded growth of pending frames, retained notes, or generated artifacts. These objective checks are more informative than a target token-throughput number.

The exact acceptable foreground delay and automatic power budget are user-facing choices. Configure and report them. The existing 60-second model turn is an upper contract, not a claim that waiting that long behind background work feels interactive. Qualify a useful background operating point without constant kill/reload churn.

## Tests and provenance

Bind tests to the real source modules, not an installed sibling. Use fake backends for controller logic, actual sandbox tests for isolation, and real model tests only for model behavior. CPU fixtures cannot establish GPU eviction or actual Qwen quality. GPU-summary samples cannot establish PID stability; use verified supervisor/resource receipts for those assertions.

The provided synthetic baseline tests are intentionally incomplete: they pass while a fixture odd-tail defect remains. The intended experiment is to create a new discriminating test in scratch space, not to count the existing green suite as correctness proof. Synthetic timing data is not hardware measurement.

Every release report lists: implemented cases, executed tests with counts, current source/config identities, model/binary identity for real inference, effective settings, before/after measurements, remaining omissions, permissions used and production changes. Material limits and failed experiments remain visible.

## Migration and activation

Revalidate open tasks and ongoing edits before acquiring scope. Preserve existing PCE2 and AS1 work unless the operator explicitly resolves overlap. Package records are new intent, not an automatic supersession of prior work.

For runtime relocation, inventory imports, scripts, frozen candidate contents, entry points, service launchers, source checks, catalog entries and test/qualification consumers. Keep one canonical implementation. Verify the forwarding path before deleting old implementation bodies, and retain historical reference material with an explicit status. Do not copy the Todo kernel into Project Control.

For persistent-state changes, prefer additive service-private records where old consumers are safe. Where record/state compatibility changes, use an explicitly versioned broker and quiescent transfer. An old process must not claim new work or misparse a new waiting state. Preserve previous jobs, exact public cache knowledge where compatible, and packet provenance. A stale release identity must park rather than repeatedly consume attempts.

Build one selected candidate after fast tests and quality selection. Confirm HTTP and fresh stdio clients share the same owner and authority. Turn automatic work off for cutover; validate normal queries, a suspend/resume journey, CLI controls and a representative permitted experiment. Re-enable only user-approved focus windows.

Rollback restores the prior runtime/launcher without restoring an old Todo database over newer work. Retain new state and artifacts for diagnosis. If a prior runtime cannot interpret new private state, preserve it separately and use its compatible state path; do not relabel new results as old-format evidence. Failed resource cleanup blocks release rather than freeing an unverified slot.

## Stop or reduce scope when value is absent

Keep the derived notebook and direct context assistance even if speculative automatic experiments do not justify their cost. Keep demand-only mode even if the watcher performs poorly. Leave native KV persistence, reactivated legacy coding delegation, new MCP tools and rich UI outside v1 unless a measured gap requires them. A smaller coherent product is a successful outcome, not a failed approximation of the brainstorm.
