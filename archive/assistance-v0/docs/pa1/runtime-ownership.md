# PA1 runtime ownership decision

The receiver will own the existing `local_worker` implementation beneath
`src/project_control/local_runtime/`, preserving the supplier's sibling layout
for Python modules, configuration, schemas, and CLI support files. The Python
module identity remains `local_worker.*`; a trusted receiver binding makes its
one canonical package directory importable. Do not introduce a second module
alias or copy the Todo kernel, CUDA resource authority, or domain skills.

The source-mode and installed bindings must validate exact receiver location
and source identity before importing runtime code. A temporary explicit supplier
binding may remain only for baseline compatibility before candidate promotion.
No observer request can override the runtime root, policies, resource grants,
or serving configuration. Import and status inspection must not start a model.

Preserve existing config/schema sibling paths where practical. Replace
`__file__` depth assumptions that locate Todo/ctxpp/CUDA siblings with explicit
configured domain-tool roots. Retain dormant writable tooling as historical
compatibility material; normal delegation stays on configured Codex subagents.

Skills retirement follows receiver parity. Its old CLI/import entrypoints become
one-way compatibility forwarding into the receiver. Remove duplicate mutable
runtime source only through that authorized transition, preserving originals
and provenance for rollback. There must be no receiver-to-Skills-to-receiver
runtime dependency cycle.

The current production service remains on its verified binding until a single
candidate has passed source tests and its reversible promotion is authorized.
Per-request tuning uses source-mode state and the existing central supervisor
lease path. It never builds a private inference pool.
